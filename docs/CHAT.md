# Conversations And Messages

The chat module owns direct messages and groups, membership and roles, messages, replies, reactions, pinned messages, read markers, per-member mute/archive preferences, and authenticated attachment delivery. The UI uses the shared controls and semantic theme tokens. Conversations use URL history; conversation drafts stay in memory when switching threads and are guarded when leaving the page. Drafts and the pending outbox are never persisted to browser storage. The composer starts with one line and grows with content. Enter inserts a newline; Shift + Enter sends, with an IME composition guard and a persistent shortcut hint.

## Composition

`ChatService` keeps its existing API-client constructor and legacy `listMessages` / `sendMessage` methods. New operations follow domain service → browser API client → authenticated `/api/backend` proxy. All query keys start with `['chat']`, preserving Socket.IO invalidation. Polling refreshes authoritative state every five seconds; Socket.IO message events also invalidate it. No typing or presence indicators are invented in demo or live mode. The local pending outbox overlays authoritative reads until the server returns its ID/client ID; polling or stale reads cannot remove the visible pending message. Reconciliation keeps the same client ID key so acknowledgement never appends a duplicate or replays entrance motion. Reactions, pins, edits, and deletion project immediately into the selected message query. Operations serialize per message, so rapid toggles retain their order while other messages remain interactive. Server responses update the cache directly without refetching people or the entire chat tree; pending projections shield periodic reads and failures roll back before authoritative recovery. Mark-read uses its returned conversation directly rather than forcing another list request. Initial history and search changes skip entrance animations; genuinely new messages use the shared theme celebration duration. Reactions use a single accessible smile-menu trigger, with existing reaction counts remaining directly toggleable. Theme and device reduced-motion preferences suppress movement.

Register `handleDemoChatRequest(request, path, context.current, { empty: context.empty })` in the demo module registry before the core legacy `/chat/messages` handler. Register `handleLiveChatRequest(request, path, forward)` in the authenticated feature proxy. Register `resetDemoChatState` for global reset and `resetDemoChatAccount` for account deletion. The module respects `projectConfiguration.starterData === 'empty'` and does not initialize conversation fixtures in that mode. An explicit demo empty scenario returns empty discovery/history reads while retaining state for scenario restoration.

All new exported schemas live in `src/modules/chat/models`. The browser service validates both request and response models. The live adapter validates request shape and supported attachment bytes before forwarding. The authenticated proxy supplies origin/session/refresh behavior; credentials never enter chat models or components.

## Backend Contract

The live backend must implement the following same-path, camelCase JSON contract. The module does not silently substitute demo content when endpoints are unavailable. Backend implementations must perform authorization independently on every operation; frontend checks are presentation only.

| Method | Path                               | Request / Response                                                                                                             |
| ------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/chat/people`                     | `ChatPerson[]` of discoverable people; exclude the current account                                                             |
| GET    | `/chat/conversations`              | `ChatConversation[]`, only conversations containing the current member, newest activity first                                  |
| POST   | `/chat/conversations`              | `ChatConversationInput` → `ChatConversation`; direct conversations reuse the existing pair                                     |
| GET    | `/chat/conversations/:id`          | `ChatConversation` for a current member                                                                                        |
| PATCH  | `/chat/conversations/:id`          | `ChatConversationUpdate` → `ChatConversation`; name/description require group admin/owner, mute/archive affect only the caller |
| GET    | `/chat/conversations/:id/messages` | Chronological `ConversationMessage[]`; current members only                                                                    |
| POST   | `/chat/conversations/:id/messages` | `ConversationMessageInput` → `ConversationMessage`; `clientId` is idempotent within conversation and author                    |
| POST   | `/chat/conversations/:id/read`     | `{}` → `ChatConversation`; record server time on the caller's membership                                                       |
| POST   | `/chat/conversations/:id/members`  | `{ userId }` → `ChatConversation`; add a discoverable member as `member`                                                       |
| PATCH  | `/chat/conversations/:id/members`  | `{ userId, role: 'admin' \| 'member' }` → `ChatConversation`; owner only                                                       |
| DELETE | `/chat/conversations/:id/members`  | `{ userId }` → `ChatConversation`; group owner/admin permissions below                                                         |
| PATCH  | `/chat/messages/:id`               | `{ body }` → `ConversationMessage`; author only                                                                                |
| DELETE | `/chat/messages/:id`               | `{}` → deleted `ConversationMessage`; author only, remove attachment access                                                    |
| POST   | `/chat/messages/:id/reactions`     | `{ emoji: '👍' \| '🎉' \| '❤️' }` → `ConversationMessage`; toggle the caller's reaction                                        |
| POST   | `/chat/messages/:id/pin`           | `{ pinned: boolean }` → `ConversationMessage`; current members only                                                            |
| GET    | `/chat/attachments/:id`            | Authenticated binary response; `?download=1` requests download                                                                 |

`ChatConversation` includes `members`, `lastMessage`, `unreadCount`, `muted`, and `archived`. A direct conversation's display name is the other member's name. Member `lastReadAt` values drive read receipts; unread counts exclude the caller's messages and deleted messages. Unread state clears when the active, visible conversation has successfully loaded. Mute is a member preference for backend notification delivery; archive changes inbox placement and does not revoke membership.

Messages contain `authorId`, `author`, `body`, `createdAt`, `editedAt`, `deletedAt`, `replyToId`, `attachments`, `pinned`, and `reactions`. `ConversationMessage` echoes the submitted `clientId` (null for fixture/legacy messages). `ConversationMessageInput` accepts a required UUID `clientId`, up to 4,000 trimmed body characters, a nullable reply ID from the same conversation, and up to four attachment inputs. A message needs a body or an attachment. Deletion retains a tombstone so replies remain intelligible and removes body, attachments, pin, and reactions. Edited bodies must remain nonempty.

Groups have at most twenty members. Owners manage metadata, add members, promote/demote admins, and remove other members. Admins manage metadata, add members, and remove ordinary members. Owners cannot be removed or demoted, and actors cannot remove themselves through these endpoints. Direct memberships cannot be edited. New members can access existing group history and attachments; removed members immediately lose all access. Transfer/leave workflows are outside this contract.

## Attachments

`ChatAttachmentInput` contains `name`, `mimeType`, `size`, and canonical base64 `data`. Allowed types are JPEG, PNG, GIF, WebP, PDF, UTF-8 plain text, MP3, MP4, and WebM. Each file is between one byte and 5 MiB. SVG, HTML, executables, and arbitrary MIME types are rejected. Both demo and live adapters inspect file signatures; text rejects null bytes and malformed UTF-8. These checks validate supported container types, not media decodability or malware safety. Production attachment storage/scanning is backend-owned.

JSON request readers enforce a 29 MiB limit using both Content-Length and a counted stream before parsing. The four-file maximum includes encoded payload overhead. Hosting/reverse proxy body limits must permit this size or enforce a smaller coordinated limit. The UI uses shared UploadField validation, local preview, explicit send, and an indeterminate pending state during encoding/transfer. Send immediately moves the complete draft into a visible local outbox item and clears the composer so another message can be written. The outbox lives above the selected thread, so switching conversations preserves pending sends and failed retries. Failed sends preserve text, files, reply, and client ID on the message for an idempotent Retry Send. Changing a composer draft creates a new client ID. Network work is aborted on account change or unmount; encoding never starts a request under a later signed-in account.

Attachment URLs are same-origin `/api/backend/chat/attachments/:id`, retain cookie authentication, and never expose storage URLs or tokens. Reads recheck conversation membership and message deletion. Demo responses use private/no-store caching, `nosniff`, sandboxed content policy, and encoded filenames. Only allowlisted raster images display inline. Other file types use download disposition; audio/video have browser-native playback and explicit download links. The production backend must provide equivalent authorization, MIME, cache, filename, and disposition protections.

## Demo Ownership And Reset

Demo uses one process-local shared workspace, so a DM or group created by one account is visible to other actual members after account switching. The people directory includes active demo accounts and authored illustrative personas. Seeded conversations include only original fixture identities and selected personas; newly registered accounts receive no private conversation membership. Creating/inviting another account establishes real shared membership. The frontend clearly identifies demo polling and the absence of presence/typing.

Mute/archive are stored by conversation and user. Read times belong to individual memberships. Requests enforce membership before message, group, reaction, pin, or file access; own-message rules and admin hierarchy are enforced server-side. Group replies must reference an undeleted message in the same conversation. Attachment creation is validated atomically before files/messages enter state, and duplicate sends return the original message for the same conversation/author/client ID.

Global reset drops the entire chat workspace. Account reset removes that user's memberships, preferences, own message bodies/files, and reactions. If an owner account is removed, the first remaining member becomes owner; conversations with no remaining members are removed. Account deletion never exposes another member's private content. Demo state has process lifetime and is not durable storage or a multi-instance live messaging system.

## Verification

Follow the repository's no-tests policy. Run focused ESLint, `npm run check`, `DEMO_MODE=true npm run build`, and `git diff --check`. Manually verify direct/group creation, switching accounts, member authorization, adding/removing members and roles, messages/replies/edits/deletion, attachment rejection/preview/download/access after removal, reactions/pins, read/unread, per-account mute/archive, search, failure-preserved drafts, keyboard dialogs, mobile Back navigation, themes, and empty starter mode. Live backend publication, durable storage, notification suppression, cross-process consistency, and socket delivery require the configured live backend.
